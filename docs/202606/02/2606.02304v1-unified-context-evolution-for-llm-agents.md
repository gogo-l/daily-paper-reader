## 摘要
基于LLM的智能体可以通过结合推理与环境反馈来解决多步交互任务，但每个回合都从相同的固定上下文开始，任何在过程中发现的有用策略一旦任务结束就会丢失。现有方法要么将学习限制在当前任务中，要么将所有经验汇集到一个无类型的存储中，而不区分知识类型、不通过使用跟踪质量，也不平衡库中尚缺乏的内容。我们提出了统一上下文演化（UCE），一个无梯度的框架，它将智能体经验外化为一个不断演化的类型化可演化上下文单元（ECU）库。UCE将经验分解为四种互补类型（记忆、策略、工作流和技能），每种类型都在特定类型条件下从轨迹中生成，在决策时检索，通过重复使用结果进行评分，并在不再有价值时剪除。一个调度模块将每个周期的生成预算分配给库中最弱的类型。在两个交互式基准测试中，UCE将ALFWorld的成功率从75.4%提高到96.3%，将WebShop的任务得分从45.1%提高到61.3%，并且积累的库可以迁移到替代的actor骨干网络而无需重新训练。

## Abstract
LLM-based agents can solve multi-step interactive tasks by combining reasoning with environment feedback, yet each episode starts from the same fixed context and any useful strategy discovered along the way is lost once the task ends. Existing approaches either limit learning to the current task or pool all experience into a single untyped store, without distinguishing knowledge types, tracking quality through use, or balancing what the library still lacks. We introduce Unified Context Evolution (UCE), a gradient-free framework that externalizes agent experience into an evolving library of typed Evolvable Context Units (ECUs). UCE decomposes experience into four complementary types (Memory, Strategy, Workflow, and Skill), each generated from trajectories under type-specific conditions, retrieved at decision time, scored through repeated usage outcomes, and pruned when no longer valuable. A scheduling module allocates each cycle's generation budget toward the types where the library is weakest. Across two interactive benchmarks, UCE raises ALFWorld success from 75.4% to 96.3% and WebShop task score from 45.1% to 61.3%, and the accumulated library transfers to alternative actor backbones without retraining.

## 1. 研究的核心动机与问题背景

基于大语言模型（LLM）的智能体在执行多步交互任务时，每次任务都从相同的固定上下文（系统指令、少样本样例、工具描述）开始。任务过程中发现的环境机制、决策策略、操作流程等有用知识，在下一个任务开始时完全丢失，智能体无法从过往经验中持续获益。

现有相关方法的局限主要包括：

- **仅关注当前任务优化**：如 ReAct、Reflexion、Self‑Refine 等方法只能在单次任务内调整行为，知识不跨任务持久化。
- **知识存储形式单一**：一些跨任务知识库方法（如 ExpeL、MemRL、Voyager 等）要么把所有经验混入无类型池，要么只掌握某一种知识形式（如只存储工作流或技能），缺乏对不同功能类型知识的系统区分和管理。
- **质量追踪粗放**：通常仅通过一次性 LLM 评估判断知识质量，而缺少基于实际使用结果的持续追踪。
- **生成资源分摊缺乏策略**：何时产生何种新知识、各类型知识应分配多少生成预算，缺乏系统性调度。

论文提出了 **统一上下文演化（Unified Context Evolution, UCE）** 框架，以 **无梯度** 的方式让智能体通过维护一个类型化的、不断演化的知识库（ECU 库）实现跨任务的持续自我改进，而无需更新模型参数。

## 2. 方法论

### 2.1 核心思想

UCE 将智能体的经验**类型化地外化到可演化上下文单元（Evolvable Context Units, ECU）中**。每个 ECU 是带有功能类型、使用频率、适应度等元信息的文本知识。在决策时，从库中检索相关 ECU 注入智能体的提示（prompt），从而改变其行为；在任务完成后，根据使用结果更新 ECU 的评价值，并周期性生成新 ECU、淘汰低质量项。

该框架无需访问模型权重，仅通过修改上下文实现智能体进化，适用于所有可接收提示的 LLM（包括闭源模型）。

### 2.2 ECU 的类型体系

UCE 将经验分解为**四种互补类型**，每种类型对应不同的生成条件、检索边界与淘汰规则：

| 类型 | 回答的问题 | 生成条件 | 知识示例 |
|------|------------|----------|----------|
| **记忆 (Memory)** | 环境机制如何运作？ | 单条轨迹 | “sinkbasin 可以直接清洗可携带物品，无需开水龙头。” |
| **策略 (Strategy)** | 在特定条件下应如何选择？ | 同一任务类型的多条轨迹 | “如果 put 失败，先打开容器再重试。” |
| **工作流 (Workflow)** | 应遵循什么执行顺序？ | 同一任务类型的成功轨迹 | “找到目标→变换它→放置在目标容器。” |
| **技能 (Skill)** | 可重复使用的子操作如何执行？ | 跨任务类型的轨迹 | “搜索容器、打开封闭容器、找到目标时拿走。” |

这四种知识在智能体执行时以不同粒度协同工作：记忆解释环境机制，策略在决策分支点上提供指导，工作流给出任务骨架，技能则展开其中的具体步骤。

### 2.3 ECU 表示与适应度

每个 ECU 建模为一个五元组：

- \(z_e\)：ECU 类型（memory / strategy / workflow / skill）
- \(\tau_e\)：关联的任务类型（Skill 类型为 \(\varnothing\) 表示跨类型适用）
- \(w_e\)：自然语言检索条件（用于语义相似度匹配，不注入 prompt）
- \(c_e\)：可注入 agent 提示的知识内容
- \(f_e\)：适应度分值，按 Laplace 平滑计算：
  \[
  f_e = \frac{s_e + 1}{u_e + 2}
  \]
  其中 \(u_e\) 为累计使用次数，\(s_e\) 为累计成功信用（成功+1，失败+0，连续奖励则加原始奖励值）。新生成的 ECU 初始 \(f_e = 0.5\)。

### 2.4 知识检索

对当前任务 \(t_i\)（任务类型 \(\tau_i\)，自然语言描述 \(d_i\)），每个 ECU \(e\) 的检索分数为：
\[
\text{score}(e, t_i) = \text{sim}(h_{w_e}, h_{d_i}) + \beta \cdot \mathbf{1}[\tau_e = \tau_i] + \lambda \cdot (f_{\tau_i}(e) - 0.5)
\]
综合了语义相似度、任务类型匹配加分和质量偏差。检索时先过滤掉类型不匹配且非 Skill 类的 ECU，再在每类型内独立排名，选取 top‑K ECU 注入提示的四个专用段落中，避免单一类型挤占其他类型。

### 2.5 演化周期（Evolution Cycle）

每个周期将库从 \(L_c\) 更新到 \(L_{c+1}\)，分为五个阶段：

1. **Evaluate (评估)**：在固定的评估集上运行，不更新适应度，记录成功率。
2. **Collect (采集)**：在分离的采集集上运行，记录轨迹与奖励，并更新 ECU 适应度。
3. **Schedule (调度)**：通过知识收益调度（KYS）算法，根据库当前状态（各类型覆盖情况、适应度分布、历史收益）为每个 ECU 类型分配下一步的生成预算 \(b_c^{(k)}\)。
4. **Generate (生成)**：对预算非零的类型，使用类型专属生成提示（含高质量/低质量 ECU 正负示例、reshuffle 测试），从采集轨迹中蒸馏候选 ECU，经去重后加入库中。
5. **Cleanup (清理)**：删除累积足够使用次数但适应度低于阈值的 ECU；在每个 (类型, 任务类型) 组内，仅保留适应度最高的 ECU。

### 2.6 知识收益调度（KYS）

KYS 根据库内部结构信号（无需额外计算）决定生成资源分配，分三层：

- **Layer 1: 可行性过滤**：若某类型所有任务类型已有足够 “adequate” ECU，则该类型不再分配预算。
- **Layer 2: 需求评估**：综合未覆盖任务类型比例和平均适应度差距，计算各类型的需求 \(d_c^{(k)}\)。
- **Layer 3: 收益跟踪**：维护各类型历史收益的指数滑动平均（EMA），估计生成该类型知识的边际性能提升。
- **融合与分配**：最终得分 \(s_c^{(k)} = \alpha_c d_c^{(k)} + (1-\alpha_c) y_c^{(k)}\)，规范化后按比例分配预算，保证每类型最低份额。

## 3. 实验设计

### 3.1 数据集与环境

- **ALFWorld**：一个文本化的家居环境，包含 134 个任务，分为 6 种任务类型（Pick, Look, Clean, Heat, Cool, Pick2）。采用 2 折分层划分，评估集 67 个任务，采集集 67 个任务。
- **WebShop**：一个模拟的在线购物环境，基于 Amazon 商品数据。使用 ExpeL 发布的 100 任务子集，2 折划分，并将任务按查询关键词映射到 5 个子类型（beauty, clothing, electronics, food, home），为 UCE 的任务类型依赖提供支撑。

### 3.2 对比方法

- **ReAct**：agent 的基础推理‑行动循环，作为所有方法的基线。
- **ExpeL**：跨任务方法，从成功轨迹中提取无类型自然语言洞察池进行注入。
- **Reflexion**：每任务多次尝试（pass@3），使用反思生成自我批评进行同任务自适应。
- **三种变体 actor 主干**：NoThinking（不输出思维令牌，仅行动）、Plan‑and‑Act（第一步输出计划，后续只行动）、ReflAct（每步加入对目标状态的反思）。对比它们在空库和加载 UCE 库下的性能，测试知识库的迁移性。

### 3.3 模型与超参数

- Agent 模型：gpt‑4.1‑mini（温度 0.7，max_tokens 256）
- 生成模型：gpt‑5.2（温度 0.4，max_tokens 1024）
- 嵌入模型：all‑MiniLM‑L6‑v2
- 检索：每类型 top‑3，\(\beta=0.15,\lambda=0.1\)，去重阈值 0.85
- 生成预算：每周期总计 6 条（B=6）
- 演化循环：ALFWorld 5 个周期，WebShop 11 个周期

## 4. 资源与算力

论文明确指出 **不需要 GPU 进行训练**，所有实验基于 API 调用执行。Agent 调用量级为 **数万次**，生成器调用仅 **几百次**，但由于生成器输出较长，成为主要的耗时和成本来源。文本嵌入模型在 CPU 上运行。WebShop 服务器端需约 40 GB 内存加载商品目录和搜索索引。未提及具体的 GPU 型号或训练时长，因为方法本身是无梯度的、不涉及模型微调。

## 5. 实验数量与充分性

实验较为系统，涵盖以下维度：

- **主对比实验**：UCE（初始库与峰值） vs. ReAct、ExpeL、Reflexion，以及适配三种 actor 骨干的对比。
- **演化曲线**：展示性能随周期变化的细节。
- **单类型消融实验**：将库限制为仅某一种 ECU 类型，观察每种知识类型的独立贡献。
- **错误分析**：对 WebShop 的失败案例分类统计，对关键案例进行轨迹级别的对比。
- **统计显著性检验**：使用 McNemar 检验和 Bootstrap 重采样验证 UCE 相较于 ReAct 的提升具有显著性。
- 实验在独立划分的评估/采集集上进行，确保评估不受适应度更新污染；对比方法均在同一 actor 模型和环境下复现，比较**客观且公平**。任务数量偏小（134 和 100），但经过推理和检验后仍足以支撑主要结论。

## 6. 主要结论与发现

1. **性能显著提升**：UCE 在 ALFWorld 上将成功率从 75.4% 提升至 96.3%（+20.9 pp），在 WebShop 上将任务得分从 45.1% 提升至 61.3%，购买成功率从 30.0% 提升至 42.0%。
2. **多类型知识互补**：在 WebShop 等复杂环境中，单一类型的库远不如四类联合有效；不同知识类型可以在 agent 陷入局部陷阱时提供逃逸所需的信息。
3. **库跨 actor 可迁移**：将库用于 NoThinking、Plan‑and‑Act、ReflAct 等不同 actor 格式，均带来稳定提升，表明知识内容与提示的具体格式解耦。
4. **KYS 调度有效**：通过可视化的演化曲线和与单类型库的对比，KYS 能合理地将生成预算分配给库中最薄弱的环节，避免饱和类型占用资源。
5. **无梯度方法适用于闭源模型**：整个框架不访问模型权重，仅通过提示注入实现持续改进，对闭源 LLM 友好。

## 7. 优点

- **类型化知识体系**：首次将智能体经验分解为记忆、策略、工作流、技能四类，并赋予各自独立的生命周期管理，填补了现有方法知识形式单一的空缺。
- **基于使用的质量追踪**：采用拉普拉斯平滑的适应度分值，以实际使用结果（而非一次性评估）驱动 ECU 的保留与淘汰，更客观反映知识价值。
- **知识收益调度（KYS）**：利用库内部结构性信号决定生成预算分配，实现不同知识类型的动态平衡，避免浪费生成资源。
- **全生命周期管理**：覆盖 ECU 的生成、检索、评分、去重、剪除等完整闭环。
- **轻量且普适**：无需梯度更新，兼容任何支持提示注入的 LLM（包括闭源模型），库亦独立于特定 agent 提示格式，迁移性强。
- **实验扎实**：主对比、消融、迁移、错误分析、案例研究、统计检验等多维度分析，提升了结论的可信度。

## 8. 不足与局限

- **环境与动作空间局限**：只在 ALFWorld 和 WebShop（离散动作、文本观察）上进行评测，尚未在连续动作、多模态观察或更长规划域（如 AndroidWorld、VisualWebArena）中测试泛化性。
- **任务规模较小**：分别只有 134 和 100 个任务，KYS 的信号估计来自这些较小集合，更大规模或更长演化周期下的稳定性与退化可能性未经验证。
- **生成器能力依赖**：提升幅度的相当部分可能来自 gpt‑5.2 的高质量蒸馏能力；更换较弱的生成模型时效果是否保持，没有分离实验。
- **类型设计是人工的**：四种 ECU 类型基于先验设计，缺乏自动发现新知识类型的机制，适配全新领域时可能需要额外的人工设计工作。
- **缺乏与参数更新方法的结合**：仅靠上下文演化仍有“如何精确执行操作”的边界；结合轻量参数更新或可进一步提升。
- **在线购物任务中，部分故障（如属性选择错误）属于“如何精细操作”范畴**，UCE 在提供环境机制、决策规则和过程骨架方面更强，但无法完全解决需页面实时交互理解的细粒度问题。
