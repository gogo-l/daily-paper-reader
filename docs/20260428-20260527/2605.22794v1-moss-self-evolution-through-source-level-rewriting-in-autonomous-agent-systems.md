## 摘要
自主代理系统在部署后大多是静态的：它们不会从用户交互中学习，重复的故障会一直持续，直到下一次由人类驱动的更新发布修复。为此出现了自我进化的代理，但所有进化都局限于文本可变的人工制品——技能文件、提示配置、内存模式、工作流图——而代理的底层框架则未受影响。由于路由、钩子排序、状态不变量和调度都存在于代码而非任何文本制品中，因此一整类结构性故障在物理上无法从文本层触及。我们认为源代码级适应是一种根本上更通用的媒介：它是图灵完备的，严格超集于所有文本可变范围，通过确定性方式而非基础模型合规来生效，并且不会在长上下文漂移下退化。我们提出了MOSS，一个在生产级代理基板上执行源代码级自我重写的系统。每次进化都锚定于一组自动策划的生产故障证据，并通过确定性的多阶段流水线进行；代码修改被委托给一个可插拔的外部编码代理CLI，而MOSS保留阶段排序和裁决。通过在与候选镜像对应的临时试用工作器中重放该批证据来验证候选，然后通过用户同意门控的、原地容器替换与健康探测门控的回滚来晋升。在OpenClaw上，MOSS在无需人类干预的单个周期内将四项任务的平均评分从0.25提升到0.61。

## Abstract
Autonomous agentic systems are largely static after deployment: they do not learn from user interactions, and recurring failures persist until the next human-driven update ships a fix. Self-evolving agents have emerged in response, but all confine evolution to text-mutable artifacts -- skill files, prompt configurations, memory schemas, workflow graphs -- and leave the agent harness untouched. Since routing, hook ordering, state invariants, and dispatch live in code rather than in any text artifact, an entire class of structural failure is physically unreachable from the text layer. We argue that source-level adaptation is a fundamentally more general medium: it is Turing-complete, a strict superset of every text-mutable scope, takes effect deterministically rather than through base-model compliance, and does not erode under long-context drift. We present MOSS, a system that performs self-rewriting at the source level on production agentic substrates. Each evolution is anchored to an automatically curated batch of production-failure evidence and proceeds through a deterministic multi-stage pipeline; code modification is delegated to a pluggable external coding-agent CLI while MOSS retains stage ordering and verdicts. Candidates are verified by replaying the batch against the candidate image in ephemeral trial workers, then promoted via user-consent-gated, in-place container swap with health-probe-gated rollback. On OpenClaw, MOSS lifts a four-task mean grader score from 0.25 to 0.61 in a single cycle without human intervention.

### 2. 论文提出的方法论

MOSS 是一套在生产级代理基板（以 OpenClaw 为例）上执行源代码级自我重写的系统。其核心思想可概括为“**故障证据驱动、多阶段流水线编辑、运行时验证、安全热替换**”。

- **整体架构（五个核心组件）**：
  - **主容器（moss-gateway container）**：运行面向用户的代理、进化服务及绑定的 moss CLI。
  - **控制界面（moss CLI + webhook）**：通过 `moss evo` 子命令将全部进化生命周期暴露给代理和用户；进化完成等异步通知通过 webhook 注入代理对话。
  - **外部编码代理 CLI**：可插拔的代码编辑模块（内置四个实现：Claude Code、OpenAI Codex、DeepSeek-TUI、OpenCode），在进化各阶段由守护进程作为子进程调用。MOSS 仅负责阶段编排与裁决，不介入具体代码修改。
  - **守护进程（host-daemon）**：驻留在宿主机上的异步进程，负责编码代理调用、临时试炼容器生命周期、容器构建与镜像管理、自动会话扫描、以及最终的安全容器替换与回滚。
  - **临时试炼容器（trial workers）**：每次迭代中，使用候选镜像启动的短暂容器，用于重放失败批次并验证候选代码的运行时表现。

- **进化流程（明确的多层级闭环）**：
  - **证据收集**：通过定时扫描用户会话（`moss evo catch-up`）或用户主动标记（`moss evo flag`）自动生成一个**生产故障批次**。每个批次锚定一个特定的失败场景。
  - **迭代进化循环**：
    1. **预循环基线**：对失败批次的原始对话记录进行任务评估，锁定用于后续比较的关键点矩阵。
    2. **七阶段流水线**（单次迭代）：
        - **定位（Locate）**：读取基线轨迹，输出诊断，不提出修复。
        - **计划（Plan）**：确定根因和修复范围（文件、逻辑、不变部分）。
        - **计划审查（Plan-Review）**：作为质量门控，批准/拒绝/要求扩量，可与计划阶段多轮循环。
        - **实现（Implement）**：在代码仓库中落地为一个 git 提交。
        - **代码审查（Code-Review）**：对照计划审查 diff，可与实现阶段多轮循环。
        - **任务评估（Task-Evaluate）**：通过试炼容器重放批次任务，按四个等级（strong/adequate/weak/missing）评分关键点。
        - **裁决（Verdict）**：综合关键点矩阵输出四个终态之一：已收敛、需要更多工作、模型能力极限、架构极限。若出现平台期，强制收敛。
    3. **评估与闭环**：循环在批次被修复或无改进时退出，最终产生一个候选镜像。
  - **安全部署与回滚**：
    - 收敛后经用户同意（`moss evo apply`）触发**原地容器替换**。宿主守护进程将当前容器替换为候选镜像，并保持用户状态卷挂载不变。
    - 替换后执行 90 秒**健康探测**（心跳、容器状态、基板 CLI 探测），连续三次通过即提交，否则**自动回滚**至上一已知良好镜像。探测失败不会陷入无限回滚循环。

- **关键技术理念**：源代码修改是图灵完备的，决定了其“进化范围”严格超集于任何文本层面的人工制品修改，因此可以修复从路由逻辑到并发状态的任何代码级缺陷。
